# Google Apps Script export prototype

A separate Apps Script web app that uses the **native Google Docs advanced service** (`Docs.Documents.create/get/batchUpdate`). It can be opened directly or embedded from MegaDoc to create a Google Doc or conservatively overwrite an eligible existing Doc. The code has local mock tests but has **not been deployed or tested against a real Google account/API**.

## Setup and deployment

1. At [script.google.com](https://script.google.com/), create a standalone Apps Script project. Paste `Code.gs` into `Code.gs` and create an HTML file named `Index` with the contents of `Index.html`.
2. Under Project Settings, show the `appsscript.json` manifest and replace its contents with this directory's manifest. It enables the Docs advanced service and the broad `documents` OAuth scope. If using a standard Google Cloud project, also enable the Google Docs API there. Save the project.
3. Deploy > New deployment > Web app. Choose **Execute as: User accessing the web app**, and select the narrowest access appropriate for your use. Open the `/exec` URL and authorize as the user who will create/edit documents. Google may show an unverified-app warning; organization policies may prevent authorization. Deploy a new version when changing source; the test `/dev` URL is restricted to project editors.
4. In Apps Script **Project Settings → Script properties**, add `MEGADOC_ALLOWED_ORIGINS` with a JSON array of trusted MegaDoc origins, for example `["https://chibbit-99.github.io"]`. For local development, e.g. `["http://localhost:8000"]`. Use origins only: no path, trailing slash, or `*`. These are public configuration values, not secrets. Deploy a new version after source changes; ensure the property is set before testing.
5. Open the `/exec` URL directly, sign in, and copy the **HTML-service origin** shown by the exporter (for example `https://n-…-script.googleusercontent.com`). The displayed value is the page's effective origin, which can differ from `script.google.com` and can change across deployments or accounts. Check it independently from your own trusted deployment; don't use an origin supplied by an untrusted party.
6. Open MegaDoc as a top-level page. Choose **File → Export current tab to Google Docs**, enter your deployment URL and the exact HTML-service origin, review the warning and select **Send tab and open exporter**. Alternatively, set both `appsScriptUrl` and `htmlServiceOrigin` in root `google-docs.config.json`. This JSON is public, not per-user or secret. Confirm these values again if the deployment or origin changes.
7. Review the received text and choose Create. For an existing document, paste its URL or ID, inspect, review the displayed target and type its exact title to confirm. Back up anything important first. The direct web-app URL also allows manual paste of text or structured JSON. If the transfer fails, use **Export current tab as text** in MegaDoc and paste it into the directly opened app.

The app requests `https://www.googleapis.com/auth/documents`, which can access **all Google Docs available to the authorizing user**, not just the selected one. Inspect the code and only authorize a deployment you trust; do not execute a public deployment as the owner. You can revoke access in your Google Account security settings. Apps Script and Google's services process the exported content; this code intentionally does not log document content. Consult Google's retention and privacy policies and your deployment's access controls. No credentials or access tokens should be placed in source, URLs, or MegaDoc configuration.

## Format and limits

Plain text is split into paragraphs. A structured JSON input can specify headings and inline styles:

```json
{"version":1,"title":"Notes","blocks":[{"kind":"HEADING_1","runs":[{"text":"Heading"}]},{"kind":"NORMAL_TEXT","runs":[{"text":"Hello ","style":{"bold":true}},{"text":"world","style":{"link":"https://example.com"}}]}]}
```

Each block is `NORMAL_TEXT` or `HEADING_1` through `HEADING_6`; runs accept `bold`, `italic`, `underline`, `strikethrough` booleans and HTTP(S) `link`. Positions use UTF-16 units, as required by Docs. Maximum 500 paragraphs, 1,000 runs and 100,000 UTF-16 units including paragraph breaks. These are application safety limits, not a guarantee of Google API capacity. Titles are 1–120 characters. Control characters, embedded newlines in runs and invalid surrogate pairs are rejected. Empty paragraphs have an empty `runs` array. MegaDoc sends rendered plain text, converted to normal paragraphs; no HTML or rich formatting converter is implemented here. Images, tables, lists, comments, footnotes, colors, fonts and other rich features are not exported. Text/paragraph styling beyond this subset may be inherited from the target. Do not use this as a lossless backup; keep the MegaDoc JSON backup.

## Overwrite safety and limitations

Overwrite first reads the complete tab tree with inline suggestions and included comments, and rejects multi-tab documents, comments, suggestions, named ranges, headers, footers, footnotes, inline/positioned objects, lists and non-text body structures. Unsupported or inaccessible inspection fails closed. The Docs API's comment-inclusion support may require enrollment in Google's Workspace Developer Preview or may not yet be available to the Apps Script advanced service; if so, **overwrite will refuse to proceed**, not fall back to an unsafe inspection. Creating a new Doc does not depend on this feature.

A user-scoped, five-minute, one-use confirmation binds the target revision and content. On confirmation the app re-inspects the document, then sends deletion, insertion and styling in a single batch with `requiredRevisionId`; concurrent changes cause failure. A timeout or other API error can leave the result unknown, so inspect the document before retrying. Creating a document and filling it requires two calls; if the second fails, the app links the possibly empty/partially updated document. Google Docs version history may allow recovery, but is not a substitute for a backup. This is a prototype, not a guarantee against all Google Docs features or API behavior changes; the overwrite path needs real-account verification before production use.

## Iframe, privacy and security limitations

MegaDoc loads the `/exec` URL with only a random request identifier, then waits for a ready message from the nested HTML-service iframe. It checks the explicitly configured exact Google HTML-service origin, verifies the sender is a descendant of the exporter iframe, and sends the tab only to that frame and exact origin. The Apps Script page accepts a message only from the top-level window at an origin configured in `MEGADOC_ALLOWED_ORIGINS`, with the same request identifier. It acknowledges receipt; no Docs write happens until the user clicks an action. The request ID correlates the messages; **it does not authenticate a deployment**.

Document content is not placed in the URL or intentionally logged. It still leaves the browser for the trusted Apps Script deployment and Google Docs when exported. Pinning an origin and checking the frame tree do not independently prove which deployment is running or prevent an already-compromised trusted host or deployment from reading the content. Verify the deployment and origin yourself and do not use this prototype for sensitive data without reviewing and testing it. A stale/changed HTML-service origin, changed Google frame structure, opaque origin, sign-in prompt, browser third-party-cookie policy or an unconfigured allowlist will cause a timeout instead of an insecure wildcard fallback. MegaDoc itself must be top-level for this protocol; if it is embedded, open it in a top-level tab.

Apps Script HTML Service uses an iframe sandbox with `allow-scripts` and `allow-same-origin` ([Google's restrictions](https://developers.google.com/apps-script/guides/html/restrictions)); nested HTML-service frames can communicate with a top-level embedding page using `postMessage` ([example discussion](https://stackoverflow.com/questions/56400233/navigating-embedded-google-apps-script-iframe-from-the-parent)). This implementation follows that approach, but the exact Google redirect/frame chain and origins have **not been tested on a real Apps Script deployment**. Chrome, Firefox, Safari, mobile and Google Workspace policies still need real-account testing.

The script enables `XFrameOptionsMode.ALLOWALL` so it can be framed. **Any site can frame the deployment**, and the message allowlist is not a complete clickjacking defense. The exporter’s buttons can be disguised by a malicious site even if that site cannot send it a tab. Restrict deployment access, open it directly if in doubt, and do not execute a public deployment as the owner. Sign-in and consent may require opening the deployment directly in a new tab. The direct fallback link contains no document text; paste a local text export there if the handshake fails. The root `GOOGLE_DOCS_EXPORT_PLAN.md` describes longer-term safeguards and conversion goals.

## Local checks

Run `node google-apps-script/tests/server.cjs` and `node --check < google-apps-script/Code.gs`. To test the integration UI, install `jsdom` outside the repository (for example `npm install --prefix /tmp/megadoc-test jsdom`) and run `NODE_PATH=/tmp/megadoc-test/node_modules node tests/google-docs.cjs`. These tests use mocks and jsdom; they do not verify authorization, real iframe redirects, deployment, Google API compatibility or actual rendered Docs.
