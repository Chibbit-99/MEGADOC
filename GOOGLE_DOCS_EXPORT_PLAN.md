# Plan: Google Docs export through an Apps Script web app

**Status: planning only.** MegaDoc currently remains local-first; this would be an optional integration requiring a user-configured deployment and Google authorization. No Google credentials, tokens, document IDs, or deployed URLs belong in this repository. A MegaDoc tab is not the same thing as a Google Docs tab.

## Goal and user flow

1. Offer **Export current tab to Google Docs**; never send the entire MegaDoc tab tree or modify the local document. Tell the user that content leaves their device and that conversion may be imperfect.
2. Read the Apps Script deployment URL from a local JSON config file. If it is absent or invalid, explain how to configure the feature; leave normal local editing/export usable. Show the configured destination host and ask before sending content. Only permit HTTPS and the expected Apps Script deployment URL shape; reject credentials, unexpected protocols, and unapproved origins. Treat the configured deployment as a trusted third party capable of receiving the user's document.
3. Open an in-app modal containing the Apps Script web app in an iframe. Provide a separate top-level popup/link for authorization if the Google login or consent screen cannot run inside an iframe. Show blocked-popup, denied-consent, expired-session, and third-party-cookie/storage failures clearly; offer a manual retry or a top-level fallback. Never request a password or token in MegaDoc.
4. Let the user choose **Create new document** or **Overwrite existing document**, with an explicit document URL/ID and a clear final confirmation for overwrite. Show the destination title, account when reliably available, and precisely what will be replaced; cancellation performs no writes. Return the resulting document link or a useful error to the modal.

## Feasibility gate: iframe, authorization, and URL parameters

Prototype this first with a real test deployment and accounts, before promising it will work. Apps Script HTML Service can be framed with `HtmlOutput.setXFrameOptionsMode(HtmlService.XFrameOptionsMode.ALLOWALL)`, but this removes a clickjacking defense and requires additional protection. Apps Script web apps and their HTML-service frames can involve redirects and different Google-controlled origins. Google sign-in/consent, third-party cookies, popup blockers and browser privacy settings may prevent the iframe flow. Verify Chrome, Firefox, Safari and mobile behavior, including deployment revisions and Google Workspace account policies. Do not silently switch to an owner-privileged deployment when user authentication fails.

The requested URL-parameter transport is possible only for **small, explicitly approved exports** and has serious limitations:

- After authentication, create an iframe URL with URL-encoded parameters such as `?action=create&payload=<encoded-json>` via `URL` and `URLSearchParams`. Apps Script receives the query in `doGet(e).parameter`; do not use its reserved `c` or `sid` parameter names. The payload can contain a version, title and sanitized content representation. Never interpolate it into executable HTML; serialize/escape as data. Do not put credentials or bearer tokens in the URL.
- Query strings may appear in browser history, web-server/Google infrastructure logs, monitoring, redirects, referrers, and screenshots. HTTPS does not remove these exposures. Explain this clearly and require explicit consent **before constructing or loading a content-bearing URL**. A referrer policy and avoiding logs reduce exposure but do not eliminate it. Do not auto-send sensitive content or report payloads in error telemetry.
- There is no portable maximum URL length across browsers, intermediaries, or Apps Script. Set a conservative *encoded full-URL* byte cap (initially 2 KiB, subject to measured compatibility), check before loading, and reject rather than truncate. This makes query export unsuitable for most real documents, especially images. Test non-ASCII, emoji, percent encoding and redirects. Do not split confidential content across many URLs or fall back silently.
- For larger or sensitive content, design a separate explicit `postMessage`/`google.script.run` transport rather than a URL: the parent and the verified iframe exchange a one-time request ID, versioned message and bounded payload. This is a proposed alternative requiring a user-facing choice/approval, not a claim that URL parameters can safely carry unlimited content. A URL fragment does not reach `doGet` as a query parameter and must not be assumed to survive Google redirects without testing.

## Configuration and trust boundaries

- Add an optional, documented JSON file such as `google-docs.config.json` containing only public deployment configuration, for example `{"appsScriptUrl":"https://script.google.com/macros/s/DEPLOYMENT_ID/exec"}`. The value shown is a placeholder, not a credential. Publish a template and validate the parsed schema and URL. Explain that a static public JSON file is visible to everyone and is not per-user secret storage.
- Define an exact allowlist for the MegaDoc origin in the Apps Script deployment itself. For messages, check `event.origin`, `event.source`, message schema, request ID and expected state on **both** sides; send responses to an explicitly verified exact origin, never `*` for document content. The nonce correlates requests and is not authentication. Do not trust an origin supplied in a URL or message. Since the final HTML-service origin may vary after redirects, establish and verify the actual deployed origin in the prototype; if a safe exact-origin handshake is not possible, do not ship the iframe transport. A Google domain by itself is not proof that the page is the intended deployment.
- `ALLOWALL` makes framing broadly possible; origin/source validation, a constrained handshake, explicit user interaction, and server-side authorization checks are required, and must be reviewed as clickjacking defenses. Never accept a message from an arbitrary embedding site or execute writes merely because an iframe loaded.
- No content or tokens in logs, analytics, browser storage, error messages, or config. Apply strict payload size/type validation on both client and server, timeouts, bounded queues, clear error handling and cancellation. Keep Google tokens inside Google's authorization/runtime mechanisms. If the configured web app URL is changed, require a new trust confirmation.

## Apps Script and Docs API

1. Create a standalone Apps Script project with an HTML-service UI, `doGet(e)`, and narrowly scoped server functions called asynchronously through `google.script.run` success/failure handlers. Deploy as a web app **executing as the user accessing it**, with access restricted appropriately for the intended audience. Configure the linked Cloud project, OAuth consent screen, approved test users, deployment version and required APIs/advanced services. Ask for the least scope that actually supports the chosen flow: investigate `drive.file` for explicitly selected files first; use broader Docs/Drive scopes only if necessary and explain/verify them. A pasted ID alone might not grant per-file scope access. Handle denied scopes and unverified-app/Workspace policy restrictions.
2. Parse and validate the current tab's exported HTML into a constrained intermediate document model. Do not execute HTML, fetch arbitrary remote resources or pass it directly to Docs as if the API imported HTML. Build and test a mapping to Docs API requests: plain text and paragraphs first, then text styles, headings, links, lists and tables where feasible. Docs indices are UTF-16 offsets; handle surrogate pairs, line breaks and shifting indices. Define explicit losses and warnings for unsupported images, equations, footnotes, MegaDoc-specific links, nested tabs, comments and history. Remote image fetching and Drive conversion, if ever added, need separate consent and security review.
3. **Create:** create a blank Google Doc using the Docs API, apply the converted content, and return its URL. Handle failure after creation explicitly (report the possibly empty/partial new doc; do not claim success).
4. **Overwrite:** retrieve the target with `includeTabsContent=true`, verify edit permission, inspect its revision and tab structure, preview the title and exact scope, and request explicit confirmation. Initially reject multi-tab documents or other structures that cannot be replaced safely; do not silently overwrite only the first tab while calling it a whole-document replacement. Define a policy for existing headers, footers, footnotes, comments and named ranges before supporting them. Recommend that users make a backup and explain Google revision-history limitations.
5. Where feasible, generate one validated `documents.batchUpdate` containing deletion and insertion/style requests, with the chosen Google tab ID and `writeControl.requiredRevisionId`. Respect Docs API range rules, including the required final newline; reject unsupported structures, oversized requests, or revision conflicts **before destructive writes**. A single batch is atomic, but a sequence of batches or create-plus-update is not: do not promise rollback or silently retry an overwrite after an ambiguous timeout. For content requiring multiple batches, either refuse overwrite or design and test an explicit recovery/backup procedure first.
6. Keep any local MegaDoc-to-Google mapping optional and separately versioned; JSON remains the complete MegaDoc backup. No automatic sync, background export, or overwrite without a fresh confirmation.

## Milestones and acceptance checks

1. **Prototype:** private test deployment; verify iframe embedding, exact-origin handshakes, authorization popup and realistic URL limits in each target browser. Record constraints and choose an approved fallback for oversized/sensitive data.
2. **Secure transport and config:** validate malformed/missing config, allowlists, spoofed origins/sources, replayed/stale IDs, cancellation, log redaction, blocked cookies/popups and permission denial. Verify CORS is not assumed to control iframe navigation; `postMessage` is origin-checked independently.
3. **Create export:** test text, formatting, Unicode/emoji, long content, empty tabs, unsupported objects, quota and API failures. Confirm the local tab is unchanged.
4. **Overwrite:** test confirmation, no permission, inaccessible/deleted doc, multi-tab rejection, revision conflicts, concurrent edits, batch validation failures, timeouts, and partial-failure reporting; never damage a test document without a recovery copy.
5. **Deployment and documentation:** publish setup instructions and a config template, list OAuth scopes and trust/privacy implications, disclose conversion limits, and test desktop/mobile and offline/no-config behavior. Keep credentials and real deployment IDs out of source control.
